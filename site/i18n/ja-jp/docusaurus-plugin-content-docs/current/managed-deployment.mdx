このガイドは、組織内の多数のユーザー向けに Tegata のオプションの監査ログを運用する管理者を対象としています。デプロイ構成の選び方、ユーザーが所有者識別子で自分を識別する方法、生の個人データを保存せずに監査履歴と Docker コンテナーを担当者に対応付ける方法を説明します。

自分のマシンで 1 人で監査ログを使用している場合、このガイドは不要です。代わりに[監査ログの有効化](scalardl-setup.mdx)を参照してください。

## デプロイ構成を選択する

Tegata は、複数ユーザー向けの監査ログについて 2 つの構成をサポートしています。どちらも、ユーザーごとに Docker Engine を実行する必要はありません。

**共有スタック (推奨される既定の構成):** 組織全体で 1 つの ScalarDL Ledger デプロイを実行します。各ユーザーのボールトは、それぞれ独自の HMAC シークレットを持つ個別の ScalarDL エンティティとして接続し、各エンティティのイベントは専用のコレクション (`tegata-audit-<entity_id>`) に保存されます。運用、バックアップ、監視が最も簡単な構成です。

**分離スタック:** チームまたはユーザーごとに個別の ScalarDL Ledger デプロイを、同じ Docker ホストまたは別のホストで実行します。各デプロイは独自のデータベース、ポート、Docker Compose プロジェクトを持ちます。あるグループの監査データを他のグループのデータと同じ場所に保存してはならないというポリシーがある場合に使用します。

次の表を参考に判断してください。

| 要件                                                     | 共有スタック | 分離スタック |
| -------------------------------------------------------- | ------------ | ------------ |
| 運用・バックアップするサービスが最も少ない               | はい         | いいえ       |
| すべてのユーザーの監査履歴を 1 か所で検索できる          | はい         | いいえ       |
| コンプライアンスやデータ所在地のためにチームごとに DB を分ける | いいえ | はい         |
| レジャーが侵害されても影響は 1 チームのレコードに限られる | いいえ       | はい         |
| 1 台の Docker ホストで動作する                           | はい         | はい         |

まずは共有スタックから始めてください。特定のコンプライアンス、データ所在地、または影響範囲の要件がある場合にのみ、チームを分離スタックに移行します。

:::warning[同梱のワンクリックスタックを共有サーバーとして使用しないでください]

`tegata ledger start` と GUI が作成する Docker スタックは、1 台のマシンを使う 1 人のユーザー向けに設計されています。固定のホストポート (5432、50051、50052) を使用するため、ホストごとに 1 つしか実行できません。また、開発用の HMAC 暗号鍵、既定の PostgreSQL パスワード、平文の gRPC を使用します。共有スタックまたは分離スタックでは、Scalar の本番環境向けガイダンスに従い、独自の資格情報と TLS で ScalarDL Ledger を実行してください。Tegata リポジトリの `deployments/docker-compose/` を出発点にできますが、これらの既定値を置き換え、分離スタックごとに異なるホストポートを割り当ててください。

:::

## ユーザーを共有スタックに接続する

共有スタックでは、各ユーザーにエンティティ ID と HMAC シークレットを割り当て、ユーザーはボールトをサーバーに接続します。エンティティ ID には `tegata-7f3a9c21` のような一意で意味を持たない値を使用してください。エンティティ ID は `tegata.toml`、ScalarDL、コレクション名に平文で表示されるため、メールアドレスや社員 ID を使用しないでください。個人への帰属には、次のセクションで説明する所有者識別子を使用します。

ユーザーは、管理者から提供された値を使用して、ボールトディレクトリの `tegata.toml` に次のような `[audit]` セクションを追加します。

```toml
[audit]
enabled           = true
server            = "audit.example.com:50051"
privileged_server = "audit.example.com:50052"
entity_id         = "tegata-7f3a9c21"
key_version       = 1
secret_key        = "<発行したシークレット>"
auto_start        = false
```

次に、ユーザーは `tegata ledger setup` を実行します。Tegata はシークレットを登録し、コントラクトを確認し、シークレットを暗号化されたボールトに保存します。セットアップが成功したら、シークレットがドライブ上に平文で残らないよう、ユーザーは `tegata.toml` から `secret_key` の行を削除する必要があります。

`tegata ledger setup` は特権ポートを通じてシークレットを登録します。特権ポートに到達できるクライアントは新しいエンティティを登録できるため、信頼できるネットワーク上でのみ、またはオンボーディング中にのみ公開してください。

## 所有者識別子を設定する

所有者識別子は、ボールトの監査イベントを担当者に結び付けます。各ボールトには 2 つの識別子を保存できます。

- **社員 ID:** 組織が発行する社員 ID または安定した UUID。推奨される主要識別子です。
- **メールアドレス:** 組織が社員 ID を発行していない場合、または相互に照合できるよう社員 ID と併用する場合に使用します。

両方を持っているユーザーには、両方を入力するよう依頼してください。両方が設定されている場合、所有者の対応付けには社員 ID が優先され、メールアドレスは補助的な値として記録されます。

ユーザーは 3 つのインターフェースのいずれかで識別子を設定できます。

- **CLI:** `tegata owner set` ([`tegata owner`](cli-reference.mdx#tegata-owner) を参照)。
- **TUI:** **設定** > **所有者識別子**。
- **GUI:** **設定** > **所有者識別子** > **識別子を編集**。

Tegata は組織固有の形式を強制しません。両方の値の前後の空白を削除して Unicode 正規化形式 C (NFC) に変換し、メールアドレスを小文字に変換し、社員 ID の大文字と小文字は維持します。NFC に変換することで、アクセント付きの文字やかなは、入力方式が 1 文字として入力しても、基底文字と結合文字の組み合わせとして入力しても、同じハッシュになります。値は最大 256 文字で、制御文字を含めることはできません。メールアドレスには `@` が含まれている必要があります。

:::tip[共有スタックでは識別子にプレフィックスを付ける]

複数の事業部門が 1 つのレジャーを共有している場合、2 人が同じ社員 ID を持つことがあります。レジャー全体で識別子が一意になるよう、`acme-emp-12345` のように組織または子会社のプレフィックスを付けるようユーザーに依頼してください。

:::

## 識別子の保護方法

Tegata は生の社員 ID やメールアドレスを保存しません。ユーザーが識別子を保存すると、Tegata はそれを正規化してハッシュ化し、ハッシュのみを暗号化されたボールトに保存して、生の値を破棄します。

既定では、ハッシュは正規化した値の SHA-256 です。ハッシュ化によって識別子は一見してわからなくなりますが、候補となる ID やメールアドレスの一覧を持っている人はハッシュを再計算して照合できます。レジャーのデータベースを入手した人が社員名簿と照合できないようにするには、組織のソルトを設定します。すべてのユーザーのドライブ上の `tegata.toml` の `[organization]` セクションで `identifier_salt` を設定してください。

```toml
[organization]
identifier_salt = "<シークレット管理ツールで生成したランダムな値>"
```

所有者識別子に対応したバージョンの Tegata で作成したボールトには、`identifier_salt` がコメントアウトされた `[organization]` セクションがすでに含まれています。その場合は、2 つ目の `[organization]` ヘッダーを追加せずに、その行のコメントを解除して値を設定してください。セクションが重複すると `tegata.toml` が無効になります。CLI は `parsing tegata.toml` エラーで停止し、GUI は既定の設定にフォールバックするため、ソルトと監査の設定が無視されます。ファイルを編集した後は `tegata config show` を実行してください。すべての値に `(default)` と表示される場合は、ファイルを解析できていません。

ソルトが設定されている場合、Tegata はソルトを鍵とする HMAC-SHA256 を使用します。ハッシュを比較できるよう、すべてのユーザーが同じソルトを使用する必要があります。ソルトがレジャーに送信されることはありません。Tegata は `[organization]` セクションを書き換えないため、レジャーのセットアップを実行してもソルトは削除されません。

ハッシュは元に戻せないため、ソルトを変更すると既存のハッシュは変換できません。識別子を再入力するようユーザーに依頼してください。ソルトの変更後にユーザーが一方の識別子だけを編集すると、Tegata は変更を検出して両方の再入力を求めるため、異なるソルトで作成されたハッシュが 1 つのボールトに混在することはありません。

次の表は、識別子の各形式が表示される場所を示しています。

| 形式               | 表示される場所                                                                                                   |
| ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| 生の値             | ユーザーが入力している間のメモリー内のみ。Tegata がディスク、ログ、レジャー、ラベルに書き込むことはありません。 |
| 完全なハッシュ     | 暗号化されたボールト、ScalarDL 内の監査イベントのコンテンツとメタデータ、Docker コンテナーのラベルとボールトごとの `docker-compose.yml`、`tegata history --json` の出力。 |
| 先頭 12 文字       | `tegata owner show`、TUI と GUI の設定画面。                                                                     |
| 組織のソルト       | `tegata.toml` (`[organization]` セクション) のみ。                                                               |

## ボールトとコンテナーを担当者に対応付ける

担当者のハッシュを調べるには、すでに把握している識別子から、Tegata と同じ正規化 (前後の空白を削除して NFC に変換し、メールアドレスは小文字にする) を行ったうえでハッシュを計算します。ASCII 文字だけで構成される識別子はすでに NFC です。それ以外の識別子は、ハッシュを計算する前に NFC に変換してください。たとえば `python3 -c 'import sys, unicodedata; print(unicodedata.normalize("NFC", sys.argv[1]), end="")' "$ID" | sha256sum` を使用します。

```bash title="組織のソルトを使用しない場合"
printf %s "acme-emp-12345" | sha256sum
```

```bash title="組織のソルトを使用する場合"
printf %s "acme-emp-12345" | openssl dgst -sha256 -hmac "$TEGATA_IDENTIFIER_SALT"
```

macOS では、`sha256sum` の代わりに `shasum -a 256` を使用してください。

### レジャー内

所有者が設定されたボールトが記録するすべての監査イベントには、認証済みのコンテンツに所有者のハッシュ (`owner_employee_id_hash`、`owner_email_hash`、`owner_hash_scheme`) が含まれます。主要なハッシュはトップレベルの `owner_hash` メタデータフィールドにも保存されるため、コンテンツを解析せずに検索できます。`tegata verify` は `owner_hash` を認証済みのコンテンツと照合するため、このフィールドを編集してイベントを別の人に付け替えようとしたり、フィールドを削除して所有者での検索から隠そうとしたりすると、改ざんとして報告されます。

共有スタックでは、各エンティティ ID が 1 つのボールトに対応します。所有者の対応表を作成するには、エンティティの最新イベントの `owner_hash` を読み取ります。

### Docker 内

ローカル Docker モードでは、Tegata がボールト用に作成するスタック内のすべてのコンテナーに次のラベルが付きます。共有スタックなど、管理者が自分でデプロイしたスタックのコンテナーにはこれらのラベルは付かないため、代わりにレジャー内の対応付けを使用してください。

| ラベル                        | 値                                                         |
| ----------------------------- | ---------------------------------------------------------- |
| `io.tegata.managed`           | `true`                                                     |
| `io.tegata.entity-id`         | ボールトのエンティティ ID (Compose プロジェクト名と同じ) |
| `io.tegata.owner-hash`        | 所有者の主要識別子のハッシュ                               |
| `io.tegata.owner-hash-scheme` | `sha256` または `hmac-sha256`                              |

たとえば、ある担当者に属するすべての Tegata コンテナーを一覧表示するには、次のコマンドを実行します。

```bash
docker ps -a --filter label=io.tegata.owner-hash=<ハッシュ>
```

Tegata は、スタックの作成時と、停止したスタックを起動するたびにラベルを書き込みます。以前のバージョンで作成されたスタックも対象です。ユーザーが識別子を変更すると、次回スタックが起動したとき (たとえば `tegata ledger stop` の後にボールトのロックを解除したとき) にラベルが更新されます。

## 識別子を変更する

識別子はいつでも変更または消去できます。変更はそれぞれ、新しいハッシュと以前のハッシュ (`old_owner_employee_id_hash`、`old_owner_email_hash`、およびそのハッシュ方式 `old_owner_hash_scheme`) を含む `owner-identifier-update` 監査イベントとして記録されます。変更前に記録されたイベントは記録時の識別子を保持するため、履歴は正確なまま維持され、更新イベントによって以前の ID と新しい ID が結び付けられます。

Tegata は、新しい識別子がボールトに保存された後にのみ更新イベントを記録します。ユーザーが識別子を変更したときに監査ログが無効になっている場合、変更を記録するレジャーはありません。監査ログを有効にした後に記録されるイベントには、現在の識別子が含まれます。

## 既存のボールトとの互換性

所有者識別子はオプションです。識別子のないボールトはこれまでどおりに動作します。イベントには所有者フィールドが含まれず、それらのイベントのコンテンツとハッシュは変わりません。既存のエンティティ ID、Compose プロジェクト名、ボールトごとの Docker ディレクトリーは影響を受けません。
