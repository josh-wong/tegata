## ボールトと回復

このセクションでは、ボールトの回復、パスフレーズの変更、リカバリーキーに関する質問を説明します。

### USB ドライブを紛失した場合はどうなりますか？

ボールトは Argon2id を使用してパスフレーズから派生したキーで AES-256-GCM 暗号化されています。ドライブを見つけた攻撃者は、強力なパスフレーズなしではクレデンシャルにアクセスできず、推測しようとすると多大な時間と計算コストがかかります。

クレデンシャルを回復するには、最新のバックアップを新しい USB ドライブに復元します。パスとドライブを置き換えてください。

```bash
tegata init /path/to/new-usb # 新しいボールトを作成
tegata import /path/to/backup/vault.tegata-backup # バックアップから復元
```

バックアップがない場合、クレデンシャルは失われます。`tegata export` を使用して定期的なバックアップを設定し、ボールト内のクレデンシャルを失わないようにしてください。[バックアップと回復](security-best-practices.mdx#バックアップと回復)を参照してください。

### パスフレーズを忘れた場合はどうなりますか？

リカバリーキーは、パスフレーズなしでボールトを回復する唯一の方法です。以下を実行します。

```bash
tegata verify-recovery
```

プロンプトが表示されたらリカバリーキーを入力します。キーが有効であれば、ボールトがアンロックされます。

パスフレーズとリカバリーキーの両方を失った場合、ボールトを回復できません。

保管のガイダンスと回復の保証については、[リカバリーキーの保護](security-best-practices.mdx#リカバリーキーの保護)を参照してください。

### パスフレーズを変更できますか？

はい。CLI を使用します。

```bash
tegata change-passphrase
```

または GUI の**ファイル → パスフレーズを変更**オプションを使用します。Tegata は現在のパスフレーズを求め、次に新しいパスフレーズを求めて確認します。操作はボールトのサイズに関係なく高速です。

### リカバリーキーはどのように見えますか？

リカバリーキーは `tegata init` 中にハイフン区切りの base32 文字列として表示される32バイトのランダム値です。

```bash
ABCD-EFGH-IJKL-MNOP-QRST-UVWX-YZ23-4567
```

表示通りに保管してください。`tegata verify-recovery` はハイフンの有無にかかわらずキーを受け付け、一般的な入力ミス (例: `0` と `O` の混同) に対して許容的です。

## 複数デバイスと複数ボールト

このセクションでは、複数のコンピューターで Tegata を使用すること、USB ドライブ間でボールトを共有すること、異なるオペレーティングシステムで同じボールトを使用することに関する質問を説明します。

### 複数のコンピューターで Tegata を使用できますか？

はい。ボールトは特定のマシンではなく USB ドライブに保存されています。Tegata がインストールされている任意のコンピューターにドライブを接続して通常通りボールトをアンロックします。CLI バイナリもドライブに保存できるため、インストールなしに任意のマシンで実行するために必要なすべてを1つの USB ドライブで持ち運べます。

### 複数の USB ドライブ間でボールトを共有できますか？

`vault.tegata` と `tegata.toml` を追加の USB ドライブにコピーできます。各コピーは独立したボールトファイルです。一方に加えた変更は他方に自動的に同期されません。同期を維持するには、各変更後にプライマリドライブで `tegata export` を実行し、他のドライブで `tegata import` を実行します。

軽量なバックアップルーティンとして、1つのプライマリドライブと1つのバックアップドライブを保持します。クレデンシャルを追加または削除した後にバックアップを更新します。

### 同じボールトで複数のオペレーティングシステムで Tegata を実行できますか？

はい。ボールトフォーマットはプラットフォームに依存しません。変換なしに Windows、macOS、Linux から同じボールトファイルをアンロックできます。

## クレデンシャル管理

このセクションでは、クレデンシャルの追加、編集、削除、タイプ固有の動作 (例: TOTP タイマー)、自動ロックの動作、日常的な使用のヒントに関する質問を説明します。

### Google Authenticator、Authy、または 1Password からクレデンシャルを移行できますか？

現在のリリースでは他のアプリからの自動インポートはありません。しかし、TOTP をサポートするほとんどのサービスでは、新しいシークレットを生成して再登録できます。移行するには:

1. サービスにログインして二要素認証設定に移動します。
2. 既存の認証アプリのエントリを削除します。
3. 新しい認証アプリを設定します。サービスは新しい QR コードまたは `otpauth://` URI を表示します。
4. `tegata add <label> --scan` で Tegata に追加します。

このプロセスにより以前のアプリの古いシークレットが無効になるため、一度に1つのサービスで行い、次に進む前に Tegata が有効なコードを生成することを確認してください。

### TOTP と HOTP の違いは何ですか？

どちらも IETF 標準で定義されたワンタイムパスワードアルゴリズムです。

- **TOTP (RFC 6238):** 時間ベース。現在の時刻に基づいて 30 秒ごと (デフォルト) に新しいコードが生成されます。ほとんどのサービスは TOTP を使用します。
- **HOTP (RFC 4226):** カウンターベース。リクエストするたびに新しいコードが生成され、カウンターがインクリメントされます。サービスと認証アプリは同期を保つ必要があります。HOTP はあまり一般的ではありませんが、信頼できるクロックのないハードウェアトークンやデバイスに役立ちます。

サービスが使用するタイプが不明な場合、ほぼ間違いなく TOTP です。`otpauth://` URI はタイプを指定します (`otpauth://totp/...` または `otpauth://hotp/...`)。

### チャレンジ・レスポンスクレデンシャルとは何ですか？

チャレンジ・レスポンスクレデンシャルは HMAC シークレットを保存します。`tegata sign <label> --challenge <string>` を実行すると、Tegata は保存されたシークレットを使用してチャレンジ文字列の HMAC-SHA256 (または HMAC-SHA1) を計算して署名を返します。これは、固有のチャレンジを発行して特定の署名されたレスポンスを期待することで認証を確認するサービスで使用されます。コンシューマサービスではあまり一般的ではありませんが、エンタープライズや組み込みのセキュリティシステムに登場します。

### スタティックパスワードを Tegata に追加できますか？

はい。クレデンシャルを追加する際に `--type static` を使用します。

```bash
tegata add my-api-key --type static
```

Tegata はパスワードを求めます (非表示入力)。後で `tegata get my-api-key` (クリップボードにコピー) または `tegata get my-api-key --show` (ターミナルにも表示) で取得できます。

## 監査ログ

このセクションでは、オプションの監査ログ機能について説明します。記録されるデータ、読み取れる人、エクスポート方法などが含まれます。

### 監査ログは必要ですか？

いいえ。監査ログは完全にオプションです。TOTP、HOTP、チャレンジ・レスポンス、スタティックパスワードなど、すべての認証操作は監査ログなしで正常に動作します。監査ログには Docker が必要でセットアップの複雑さが増します。認証イベントの改ざん防止記録が必要な場合にのみ有効にしてください。

### 監査ログにはどのようなデータが含まれていますか？

監査レコードには操作メタデータと整合性ハッシュが保存されます。平文のシークレットは含まれません。

完全なフィールドリストについては[監査ログが記録する内容](security-best-practices.mdx#監査ログが記録する内容)を、[`tegata verify` が証明すること](security-best-practices.mdx#tegata-verifyが証明すること)を参照してください。

### 誰が監査ログを読めますか？

監査ログはローカルの ScalarDL Ledger インスタンス (マシン上の Docker) に保存されています。マシンまたはボールトデータへのアクセス権を持つ人のみが読み取れます。

データフローとネットワーク動作については、[Tegata は外部サーバーにデータを送信しますか？](#tegataは外部サーバーにデータを送信しますか)を参照してください。

### 監査ログデータをエクスポートできますか？

`tegata history --json` を使用してすべてのイベントを JSON 配列としてエクスポートします。

```bash
tegata history --json > audit-export.json
```

フィルタリングのために `jq` にパイプしたり、ログ集計ツールに読み込んだりできます。

### Docker がオフラインの場合、キューに入れられたイベントはどうなりますか？

認証操作を実行したときに ScalarDL Docker スタックに到達できない場合、イベントは暗号化されたローカルキューファイル (`vault.queue`) に書き込まれます。キューに入れられたイベントは、次に Docker スタックに到達可能になったときにレジャーに送信されます。イベントが失われることはありません。

## プライバシーとデータ処理

このセクションでは、Tegata が収集するデータ、フォンホームするかどうか、メモリ内の機密情報の処理方法に関する質問を説明します。

### Tegata は外部サーバーにデータを送信しますか？

いいえ。すべての認証操作はデバイス上でローカルに行われます。唯一のネットワークアクティビティは、マシン上の Docker で実行されている ScalarDL Ledger インスタンスとの間のオプションの gRPC 通信です。監査ログを有効にしていない場合、ネットワーク接続は一切行われません。

記録される内容の詳細については、[監査ログのセキュリティとプライバシー](security-best-practices.mdx#監査ログのセキュリティとプライバシー)を参照してください。

### テレメトリーや分析はありますか？

いいえ。Tegata にはテレメトリー、更新チェック、分析は含まれていません。

## 貢献とコミュニティ

このセクションでは、バグの報告とコードの貢献に関する質問を説明します。

### バグを報告するにはどうすればよいですか？

プラットフォーム、Tegata バージョン (`tegata version`)、再現手順、`--verbose` からの関連出力を添付して[GitHub の issue を作成](https://github.com/josh-wong/tegata/issues/new)してください。

### コードを貢献するにはどうすればよいですか？

開発セットアップ、コーディング標準、プルリクエストプロセスについては[CONTRIBUTING.md](https://github.com/josh-wong/tegata/blob/main/CONTRIBUTING.md)を参照してください。要約: リポジトリをフォークし、`feature/` または `fix/` ブランチを作成し、テストを書いて、`main` に対して PR を開きます。
